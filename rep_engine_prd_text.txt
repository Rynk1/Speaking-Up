
PRD / Architecture Specification + Jules Implementation Prompt
Document status
Implementation authority
This specification should be treated as an architectural extension to the existing SPEAK UP WEB PRD.md, not as an optional enhancement.
It must be implemented without breaking the existing citizen-posting, public-feed, institutional-tagging, social-sharing, moderation and alerting functionality.

1. Executive objective
Implement a Privacy-Preserving Public Representation Engine (P³RE) that allows Speak Up to accept a citizen's original submission while automatically generating one or more audience-specific representations.
The central requirement is:
The original citizen submission must remain protected and intact, while public-facing representations automatically minimise or redact sensitive information according to policy.
The system must support:
ORIGINAL CITIZEN SUBMISSION
          │
          ├───────────────┐
          │               │
          ▼               ▼
 PROTECTED EVIDENCE   PUBLIC REPRESENTATION
          │               │
          │               ├── Public website
          │               ├── Search
          │               ├── Social sharing
          │               ├── OG metadata
          │               └── Public APIs
          │
          ▼
 AUTHORISED INSTITUTION
The system must never overwrite the original evidence with the redacted version.

2. Core design principle
The system must treat:
content storage
and
content presentation
as separate concerns.
A citizen submits one canonical source.
The platform creates controlled projections from it.
Therefore:
CanonicalSubmission
        │
        ├── PublicProjection
        ├── InstitutionProjection
        ├── ModeratorProjection
        ├── AISafeProjection
        └── SocialProjection
Do not create one post.content field and attempt to hide sensitive portions at rendering time.

3. Recommended economical technology stack
The objective is to use existing/common technology and avoid introducing unnecessary infrastructure.
Primary application
Use the application's existing stack.
If the current repository is:
Next.js
TypeScript
React
Node/Express API
retain it.
Do not rewrite the application simply to implement P³RE.

Recommended Google components
Google Cloud Sensitive Data Protection
Primary sensitive-data inspection/redaction engine.
Use it for:
PII detection;
text redaction;
OCR-based image inspection;
image redaction;
custom infoTypes;
structured de-identification.
Google currently supports built-in detectors plus custom dictionaries, regexes and contextual detectors.

Google Cloud Storage
Use for:
original evidence
protected evidence
public derivatives
temporary processing objects
Separate buckets or strongly separated prefixes should be used.

Gemini
Use Gemini only where semantic/contextual understanding is useful.
Examples:
determining whether a person is acting as a public official;
understanding whether a statement is an allegation or opinion;
contextual sensitivity classification;
generating public-safe summaries;
detecting implicit sensitive context that regex/DLP cannot reliably determine.
Do not use Gemini as the primary PII detector.
Do not send unnecessary raw personal data to Gemini.

Existing database
Use the application's existing database.
Do not introduce a new database solely for P³RE.

Existing authentication
Use the application's existing authentication and RBAC.
Do not create a second identity system.

Background processing
Start economically:
API
 ↓
database job
 ↓
worker
or the application's existing asynchronous/job mechanism.
Do not introduce Kafka, Kubernetes, Pub/Sub, Cloud Run Jobs, Redis, etc. unless actual scale later justifies it.

4. Why this architecture is economical
The expensive mistake would be:
Every post
→ Gemini
→ Vision AI
→ multiple LLM calls
→ video AI pipeline
→ human review
That will become unnecessarily expensive.
Instead:
Cheap deterministic detection
        ↓
Google DLP where necessary
        ↓
AI only for ambiguity
        ↓
Human review only for high-risk cases
The principle should be:
Deterministic first → specialised service second → AI third → human review last.

6. Processing states

If privacy processing fails, the system must fail closed for public publication.

15. Storage architecture
Use separate logical security zones.
Cloud Storage
│
├── original/
│
├── protected/
│
├── public/
│
└── processing/
original
Extremely restricted.
protected
Institution-authorised evidence.
public
Only safe derivatives.
processing
Temporary files with aggressive lifecycle cleanup.
Do not allow the public bucket to contain originals.

16. Object naming
Never expose predictable IDs.
Bad:
/uploads/post-123/original.jpg
Prefer opaque identifiers:
original/{submissionUuid}/{randomObjectId}
and never expose internal storage paths directly.

17. Public media access
Use the application's CDN/public delivery layer for already-public derivatives.
For protected evidence, use short-lived signed URLs or equivalent authenticated object access.
Google Cloud Storage supports time-limited signed URLs for specific objects.
However:
Do not treat a signed URL as authorisation.
The backend must first determine:
Who is requesting?
What institution?
What role?
What submission?
What access purpose?
Is access still valid?
Only then generate the signed URL.

25. Gemini's role
Gemini should perform:
Good uses
contextual classification;
ambiguous entity interpretation;
public-safe summarisation;
semantic sensitivity detection;
classification of allegation/opinion/report;
detecting implicit privacy concerns.
Bad uses
Do not use Gemini to:
determine whether an accusation is true;
determine guilt;
determine whether a person committed a crime;
make legal conclusions;
replace DLP;
replace deterministic PII detection;
decide whether an institution is corrupt.

26. Cost-control policy for Gemini
Implement:
if deterministicDetectionSufficient:
    doNotCallGemini()

elif policyRiskHigh:
    humanReview()

else:
    callGemini()
This is a major cost optimisation.

27. AI fallback behaviour
No fake AI.
If Gemini is unavailable:

Do not invent classifications.
However, deterministic privacy processing should still operate.
For example:

+

=

This is very important.
AI should be optional intelligence, not the privacy foundation.

30. Face redaction
For public content involving:

children;
bystanders;
private persons;
the policy engine can require face anonymisation.
Do not automatically blur every face in every public-interest image.
Example:
Crowd at a public demonstration
may have different requirements from:
Child victim in a sensitive incident.
This requires context-aware policy.

31. Video
Do not build sophisticated AI video redaction in Phase 1.
It will increase cost and complexity dramatically.
Phase 1:
protect original video;
extract audio;
transcribe where required;
inspect metadata;
inspect selected/key frames;
identify obvious sensitive content;
send high-risk video to human review.
Phase 2:
automated face blurring;
licence plate blurring;
OCR redaction;
audio PII redaction.
Phase 3:
full frame-by-frame automated redaction.
This is much more economical.

32. Audio
For voice notes:
original audio
     ↓
protected storage
     ↓
speech-to-text
     ↓
PII inspection
     ↓
public transcript
For MVP:
Do not automatically publish a redacted audio derivative.
Instead, if the voice recording contains sensitive information:
keep the original protected;
optionally publish a redacted transcript;
require human review for public audio.
Voice itself can be identifying, so don't assume a transcript alone solves the privacy issue.

33. Metadata stripping
This is absolutely essential and easy to overlook.
Before public media publication, strip:
EXIF;
GPS coordinates;
device information;
author metadata;
embedded thumbnails;
software metadata.
Public derivatives should contain only metadata necessary for public delivery.

34. GPS is particularly important
A citizen could upload a photo that contains:
GPS:
5.6037,-0.1870
Even if the image contains no visible address, the metadata could expose the person's location.
Therefore:
Public media derivatives must have location metadata stripped unless explicitly approved by policy.

54. Failure strategy
DLP unavailable
If existing cached deterministic rules can safely process content:
continue where safe.
Otherwise:
PRIVACY_PROCESSING_UNAVAILABLE
and hold publication.
Gemini unavailable
Continue deterministic privacy processing.
Only semantic AI features become unavailable.
Storage unavailable
Do not acknowledge upload as successfully stored.
Redaction generation fails
Do not publish original.
Institution integration unavailable
Show:
NOT_CONFIGURED
DELIVERY_FAILED
Never fake success.

76. One architectural decision I would make now
For your particular project, I would resist the temptation to build a huge "AI privacy engine."
The economical architecture is:
TypeScript rules → Google Sensitive Data Protection → existing storage/database → Gemini only for semantic ambiguity → human review for high-risk cases.
That gives you most of the capability without creating an expensive AI infrastructure project.
Google's current platform already supports the fundamental building blocks—200+ detectors, custom detectors, text de-identification, OCR/image inspection, image redaction and multiple transformation methods.
The real intellectual property of Speak Up should therefore be the policy/orchestration layer, not a proprietary AI model:
What should be visible to whom, under what circumstances, and why?
That is where the civic/privacy sophistication of the platform will reside.
And I would make P³RE a prerequisite for the final production release, particularly because Speak Up's core value proposition involves citizens uploading exactly the kind of sensitive, potentially identifying material that ordinary social platforms tend to handle poorly.
